## 一、幽灵进程：症状在「启动」，病根在「退出」

用户描述的现象是「点了没反应」，直觉会往**启动**方向查，实际病根在**退出**。

桌面壳有两个窗口：`main`（加载线上站点）和 `pet`（桌宠）。`pet` 在
`tauri.conf.json` 里是 `visible: false` 建的 —— **看不见，但它是被真实创建出来的**。
而 Tauri 的默认退出条件是「所有窗口都关闭」：

1. 点关闭 → 前端 `winClose()` → `getCurrentWindow().close()` → 主窗口被**销毁**
2. `pet` 还在 → 进程不退出 → 没有可见窗口的**幽灵进程**（任务栏没有、桌宠也看不见）
3. 再点图标 → `tauri-plugin-single-instance` 把新进程拦下（新进程自己退了），
   转而在**老进程**里跑回调，想把 `main` 拉前台
4. 可 `main` 已销毁，`getWebviewWindow("main")` 返回 `None` → 回调什么都没做
5. 用户看到「点了没反应」，只能去任务管理器

**当场抓到的现行**：`tasklist` 里有个 `jizhi.exe`（PID 36932）。它的窗口标题是
`com.jizhi.desktop-siw` —— 正是 `single-instance` 建的那个 IPC 辅助窗口
（`siw` = single instance window）。**应用真正的主窗口标题是 `JIZHI`，它不在。**
一个只剩 IPC 窗口、没有主窗口的进程 = 确诊幽灵。

### 怎么发现「装的不是最新的」

一开始只是怀疑，坐实靠的是**逐个比对时间戳**，不是读代码猜。
⚠️ **教训：报「修好了但没用」时，第一件事是比对构建产物的 mtime 和源码的 mtime**，
比读代码快得多。

### 顺带发现的两件事

- **窗口大小/位置一直没被记住** —— `window-state` 插件只在**优雅退出**时落盘，
  而进程从来没优雅退出过，所以 `%APPDATA%\com.jizhi.desktop` 一直是空的
- **强杀会丢最近的 localStorage 写入** —— WebView2 没机会刷盘

## 三、重建与打包

版本提到 **0.1.1**（`tauri.conf.json` / `Cargo.toml` / `package.json` 三处同步）。

**为什么必须提版本号**：`routers/download.py` 的 `_parse_version()` 是**从安装包文件名里
正则抠版本号**的（`JIZHI_(\d+\.\d+)_x64-setup.exe`），目录里没有任何别的元数据。
版本号不变的话，已经装了 0.1.0 的人永远收不到更新提示（`cmp = 0`）。

构建 2 分 29 秒（release + LTO + `codegen-units=1`），产出 1.55 MiB。

**换包时踩到 `download.py` 的一个设计**：`_latest_installer()` 是
`max(files, key=lambda p: p.stat().st_mtime)` —— **按修改时间取最新，不是按版本号**。
所以目录里最好只留一个 exe；留着旧的虽然眼下 mtime 更老不会被选中，
但以后手工拷文件、或从别处覆盖过来很容易把 mtime 弄错，结果线上发出旧版本。
两个仓库的 `static/downloads/` 都换成了 0.1.1，旧的删掉。

### `pack-backend.py` 的两个编码坑

打包脚本本身也修了两处，都是本机中文 Windows 的老毛病：

1. **`UnicodeEncodeError` 崩在 `✓` 上** —— 而且是包**已经写完了**才崩在最后那行
   `print`。现象是「报错但 zip 其实在」，很容易误判成打包失败。符号换 ASCII +
   `errors="replace"` 兜底。
2. **中文在 Git Bash 里全是乱码** —— Python 默认往 GBK 控制台写，Git Bash 按 UTF-8 读。
   改成显式 `reconfigure(encoding="utf-8")`。

`gen_announcement.py` 后来也补了同样的处理。

## 四、生产配置：离线关掉「先审后发」

发货前过了遍包里到底带了什么，发现一个**没人能处理的中间态**：

这版后端一上线，「内容先审后发」就生效了 —— 信誉分低于 70 的用户，新发的帖子和评论
以 `status='pending'` 落库、仅自己可见。**但后台没有审核页面**：全前端搜
`content-review` / `contentReview` **零命中**，路由、侧边栏、API 封装里都没有
（只有视频审核页 `AdminVideos.vue`，那是另一套）。管理员只能直接打 API 才能放行。

后果：一旦有人掉到 69 分以下，他的内容就**无限期卡住**，而前端还照样弹「发布成功」
（`CommunityFeed.vue:230` 写死），驳回通知也发不出去
（`system.content_rejected` 没在 `notification_registry` 里登记）。

**改法**：档位是**库里的数据**不是代码 —— `needs_review()` → `get_tier()` →
`load_rules()` 读的就是 `reputation_tiers` 表。所以改库即可，**不用重打包**：

```sql
UPDATE public.reputation_tiers SET content_needs_review = FALSE
WHERE code IN ('restricted', 'high_risk');
```

⚠️ `load_rules()` 有 **5 分钟缓存**（`_RULES_TTL = 300.0`），且全项目没有任何地方调
`load_rules(force=True)` —— 改完最多 5 分钟自动生效，重启后端则立即生效，**没有手动刷新**。

**`can_publish` 故意没动**：`high_risk`（0-39 分）发内容会当场收到 403，
而那条 403 的文案本身就把分数、档位、恢复办法说清楚了（`reputation_gate.py:154-159`），
属于「明确拒绝」而不是「卡住」。

## 五、公告：内容写一份，投两个渠道

### 两个渠道的渲染规则完全不同

| | 站内（消息中心） | 邮件 |
|---|---|---|
| 渲染 | **纯文本**，`{{ p }}` 文本插值会转义，写 HTML 无效 | HTML（`MIMEMultipart("alternative")`） |
| 分段 | 按**空行**切（`MessageCenter.vue:318-321`） | 自己排版 |
| 空格 | `white-space: pre-line` —— **保留换行，折叠连续空格** | 原样保留 |
| 配图 | **`image_url` 后端存了但前端从不渲染**（全文件零命中） | 支持 |

所以「站内比邮件精美」在**不改前端的前提下做不到** —— 站内能用的只有字符本身。
最后靠**分隔线 + 分节 emoji + 彩色圆点**做了视觉分区（🟢🔵🟡🔴 对应四档信誉色，
这是站内唯一能做出「颜色」的手段）。

**公告走 `notice` 形态**（`system.announcement` → group=system）。三个必须知道的细节：

- **列表行只显示正文前 2 行**（`-webkit-line-clamp: 2`）。首段如果写「亲爱的同学们：」
  「本次主要有四项内容」，那两行等于什么都没说 —— 所以**首段合并成一句列全四件事**。
- **标题不出现在详情里**：`bodyParagraphs` 取 `content || title`，有正文就只用正文。
- **底部只有一个「标记已读」**：`link` 为空 → 无「查看详情」；非待办 → 无「去处理」；
  system 组 `canDelete=false` → 连删除都没有（留底）。

### 投递

- **站内**：`publish_announcement.py` → 写 `system_announcements` +
  **用后端自己的 `notify_broadcast`** 广播（不重写一遍，走的就是管理后台那个按钮的同一段代码）

## 六、🎯 绕 SNI 阻断写生产库

本机网络对 `*.supabase.co` 做 **SNI 定向阻断**（TLS 握手读到域名就 reset），
直连必失败（`000`）。走 `_devtools/supabase-h3-bridge/bridge.py` —— 本地
`127.0.0.1:8787` 的 FastAPI 代理，用 QUIC 转发（QUIC 把 SNI 也加密了，中间设备看不见）。

**关键手法**：`config.py` 用的是 `load_dotenv()`，默认**不覆盖**已有环境变量。
所以脚本只要在 import 之前 `os.environ["SUPABASE_URL"] = "http://127.0.0.1:8787"`，
就能让**后端自己的代码**去打生产库 —— **一行 `.env` 都不用改**。

### ⚠️ 桥上的写操作，超时 ≠ 没写

发公告时报了 `httpx.ReadTimeout`，一度以为失败。**查库发现写入是全完成的** ——
23 条通知、23 个用户、零重复。超时发生在**读响应**阶段：桥是单条 QUIC 连接串行转发，
23 个用户一次批量插入，写进去了但响应没在 60 秒内回来。

**一般规律：桥（或任何代理）上的写操作超时，必须去目标库里核实再决定要不要重发。**
直接重试很可能写出第二份。

### ⚠️ curl 传中文 JSON 会被编码搞坏

改 `perks_text` 时用 curl 发：

```bash
curl -X PATCH ... -d '{"perks_text": "AI 生成每天限 10 次"}'
```

返回的不是数组，是一个 **4 键的错误对象**（`{"code","details","hint","message"}`）。
而脚本里写的是 `len(json.load(sys.stdin))` —— **数出来正好是「更新行数: 4」，
看着像成功**。实际一个字都没改。

**两个坑叠在一起**：shell 传中文 JSON 被编码破坏 + 用 `len()` 数响应分不清
「2 行数据」和「4 键错误」。改用 Python 的 `httpx.patch(..., json=...)` 一次就好了。

**一般规律：写接口的返回，要判 `status_code`，不要数 `len()`。**

## 教训

1. **「修好了但没用」先比对时间戳** —— 构建产物 mtime vs 源码 mtime。
   这次一眼定案，比读代码猜快一个数量级。
2. **症状的位置不等于病根的位置** —— 「点了没反应」看着是启动问题，实际是退出问题。
   幽灵进程的窗口标题（`-siw`）才是决定性证据。
3. **发货前过一遍「包里到底带了什么」** —— 「先审后发」能上线但没人能处理，
   是这次发货前唯一真正拦路的问题，靠翻包里代码翻出来的，不是靠读需求。
4. **数据驱动的开关优先用数据关** —— 档位读表，所以改一行 SQL 就够了，不用重打包。
   设计成读表的东西，运维时省一整个发布周期。
5. **一份内容两个渲染器** —— 站内和邮件的规则完全不同（分段、空格、配图），
   内容只写一份、渲染各管各的，才不会改了这边忘了那边。
6. **桥/代理上的写超时要去库里核实**，别直接重试。
7. **写接口判 status_code，不数 len()**。
