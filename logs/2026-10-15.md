## 三、🎯 恢复曲线：这是这天最需要解释的一个设计

用户中途插了一句：**「信誉值有扣分，那就有恢复，你要设计好」** —— 提醒得对。

**第一版是固定 +2 / 连续 7 天。算一下就知道不能这么干：**

> 从 0 分爬回 100 需要 50 次恢复 = **350 天**。那不叫恢复，叫永久留疤 ——
> 而误判一定会发生。

现在是一条**加速曲线**（四档全在 `reputation_rules` 表里）：

| 连续清白 | 每日恢复 |
|---|---|
| < 3 天 | 0（冷却） |
| 3–6 天 | +1 |
| 7–13 天 | +2 |
| 14–29 天 | +3 |
| ≥ 30 天 | +5 |

**性质**（设计目标，不是巧合）：从 0 回到满分约 **38 天**；轻度过失（扣 3 分）**6 天**回满；
封禁（扣 40）要**一个多月**；越清白恢复越快。全程可预期
（`next_recovery_in_days()` 能告诉用户"再坚持 N 天"）。

三条守住的规则，每条都有测试：**只发最高一档**（不是 1+2+3+5 全领）、
**恢复记录不能重置自己的计时器**（否则自锁）、**扫描一天只跑一次**（调度器 10 分钟一轮，
不挡的话每个用户每天被查 144 次）。

## 四、测试抓出的 bug（全是测试抓的，不是我复查出来的）

**① `streak_days` 的隐蔽查询 bug —— 这个最要命。**
取 `limit=1` 拿最近一条日志，再在 Python 里 `continue` 跳过恢复类记录。
**如果最近那条正好是恢复记录，跳过后就没有别的行了**，函数直接返回"从没违规过"（3650 天）。
后果：**刚恢复过一次的人，下次按最高档 +5 恢复**。
修法是把过滤挪进查询（`reason_code=not.like.recovery.*`），并加兜底：过滤万一没生效就返回 0。

**② `CHECK (delta <> 0)` 与边界日志冲突。**
0 分用户继续违规时必须留一条 delta=0 的流水 —— 不记的话，
**「连续 N 天无违规」的计时器会在持续违规期间照常走**（明明还在违规却在攒恢复天数）。
是我自己 SQL 和引擎两边写岔了。

**③ 恢复的自锁。** 恢复判定必须排除 `recovery.*` 自己，否则每次恢复都在重置自己的计时器。

**④ `peer != ip` 判据方向全反。** 直连时 `get_client_ip` 返回的**本来就是** peer、两者相等；
经代理时才是 peer(127.0.0.1) ≠ ip(真实)。照那个写法**每条正常请求都会被塞一个
`peer_ip: 127.0.0.1` 的噪音字段**。改成由 `client_ip` 直接回答「经没经代理」。

**⑤ `_check` 的 `UnboundLocalError`。** IP 取不到、user 档又不适用时 `remaining` 未绑定 ——
**本地直连调试时每个请求都会 500**。典型的"生产没事、一上本地就炸"。

**⑥ 我自己写丢了一个 `return res.json()`。** 改评论通知时把它一起替换掉了。

**⑦ 测试设计问题（不是代码问题）**：限流中间件两道闸是**串行都查**的，
第一版把一条规则设成 `ip=2 / user=3`，结果全程只测到 IP 档 —— 小的那个永远先咬。
改成两条独立规则才隔离出 user 档。

**⑧ 既有 bug：动态流从来没过滤 `is_deleted`。** 被举报删掉的帖子**一直在社区里显示**，
处置记录写着"已删除"用户还看得见。动同一个查询时一并修了。

## 六、🎯 两个"两个方向都说得通"的取舍，都刻意写进了注释

**① fail-open vs fail-closed。**

| 场景 | 取向 | 理由 |
|---|---|---|
| 发帖/评论的内容审核 | **fail-closed**（服务挂了就拒绝） | 宁可拒绝也不能放违规内容出去 |
| 网关的入闸 | **fail-open**（服务挂了就放行） | 否则审核服务一挂，**全站没人能生成任何东西** |
| 读信誉分 | fail-open（当满分） | 少拦几个帖子的代价，远小于「所有人都以为自己被封了」 |

**② 「用户可控的文本」这个区分。**

网关入闸**只查用户可控的那段**，不查整个 prompt —— system prompt 里有"政治敏感"这种字眼很正常。
不区分的话网关会天天误报，然后在 40 个调用处被逐个绕过，**那还不如不做**。
所以调用方用 `input_texts={字段名: 文本}` 显式声明。

**③ `check_content_safety` 是 fail-closed 的，这个陷阱差点踩上。**
它服务挂了也返回"不安全"。**照直挂扣分的话，模型 API 抖一下全站用户一起掉分。**
现在用 `SERVICE_UNAVAILABLE` 常量把「判定违规」和「服务不可用」分开，只有前者扣分。

## 教训

1. **🎯「要什么功能」和「缺什么防线」是两回事，先量再动手。**
   用户要的是"安全中心"，量完发现真正的问题是 77 个端点零鉴权、
   身份靠请求体自报。**做十个新功能，不如先把门关上。**

2. **🎯 一个业务改动之前，先核所有客户端怎么调它。**
   `/subject-plan/syllabi` 差点被加上鉴权 —— 而小程序和 Flutter 是以**游客身份**调它的。
   补鉴权这种事，**逐个端核一遍的成本，远小于三端一起挂的成本**。

3. **🎯 阈值不该由实现者发明，但更不该发明完就藏在代码里。**
   信誉值的分档和加减分全进了配置表 —— 这是 10-08「JUMP_DELTA=20 是拍脑袋定的」
   那条教训的兑现：**让数字可见、可改，而且改它不用碰代码**。

4. **同一个接口的两个 False 可能意思完全不同。**
   `check_content_safety` 服务挂了也返回 `False`。不区分就挂扣分的话，
   **模型 API 抖一下全站用户一起掉分** —— 而且这种 bug 在测试环境永远不会暴露。

5. **"取回一行再在代码里过滤"是个陷阱。**
   `streak_days` 那个 bug 就是这么来的：`limit=1` + Python 里 `continue`，
   跳过之后没有别的行了，函数走进兜底分支返回一个**看起来合理但完全错误**的值。
   **能放进查询的过滤，就别放到取回之后。**

6. **测试写错和代码写错一样常见，而且前者会伪装成后者。**
   这天有三次失败是**测试自己的期望值过时**（写死了 100，而前面几组已经改过那个用户的分）。
   用「前后对比」而不是「写死的数字」，能省掉这类假警报。

7. **别在不可靠的工具上反复搏斗。** 桥挂死三次之后我停手了 ——
   在一个开发用的变通工具上继续烧时间，不如**如实报告"这一步没验"**。

## 三、前端验收 = 一场 bug 猎捕（四个）

「前端在浏览器里过一遍」这条，原以为卡点是「页面是空的」。打开才发现**四个真 bug**，
而且每一个都**单测抓不到**。

### ① 时间戳里的 `+` —— 整页 502

用户报的原话是「**安全事件总览查询失败（上游 400）。若提示表不存在或权限不足，
请确认 security_center.sql 已执行。但是我执行了**」—— 表**一直在**。

根因是查询串里的一个 `+`：

```
since.isoformat()  →  "2026-10-08T12:15:57.613420+00:00"
                                                      ↑
手工拼进 URL 后，`+` 在 query string 里 = 空格
服务端实际收到:      "2026-10-08T12:15:57.613420 00:00"
PostgREST:         400 invalid input syntax for type timestamp with time zone
```

`admin_security.py` 的 `_fetch` 是**手工拼查询串**，三处调用点里：
`/overview` 的时间窗**无条件**加 → **整页挂**；`/events` 只在带日期筛选时才加 →
默认页看着好好的、**一筛选时间就挂**。

### ② `ilike.%{}%` 里的 `%` —— 社区搜索永远是「没有结果」

同一类问题的**另一张脸**。原样的 `%` 不是合法转义 → Supabase 边缘 worker 抛异常
（**Cloudflare Error 1101 → HTTP 500**）→ 被 `!= 200 → 返回空列表` 吞掉 →
**社区搜索永远显示「没有结果」，搜什么词都一样**。视频搜索、小基聊天搜索同样。

**还有一处更阴的**：`subject_plan.py` 的「今日完成度」也是这么拼的，
但失败被 `if status_code == 200` 吞掉 → **永远显示 0，不报错不冒烟**。

> 修法不是给时间戳打补丁，而是**把整类问题去掉**：所有手工拼串改成传参数字典，
> 由 httpx 负责编码。另抽 `ilike_term()` 处理用户搜索词 ——
> `%` 交给 `quote`，而 `,` `(` `)` 换成空格，**后者编码救不了**
> （PostgREST 先把整个 `or` 的值解码、再按这些字符切分）。
>
> 全仓同类写法还查出 4 处。**`admin.py` 那处本来就对** —— 作者当时用了
> `quote()` + `*` 通配符，还留了注释「手动拼接 URL（避免 httpx 编码 PostgREST 特殊字符）」。
> **知道这个坑，只是别处没照做。**

### ③ `count=exact` 是请求头，不是查询参数

社区动态流的 `total`（分页总数）**一直是 0**。根因：
`?select=id&count=exact` —— 它是 **`Prefer: count=exact` 请求头**，
写成查询参数 PostgREST 回 `PGRST100 failed to parse filter (exact)`。
一直没被发现，是因为下面只判 `status_code == 200`，非 200 就 `total = 0`。

**这是既有 bug，不是本轮引入的。** 改成请求头 + `limit=1`，总数从 `Content-Range` 读。

### ④ `streak_days` 把加分的边界流水当成违规

加分规则在满分边界也写一条 `delta=0` 流水，而 `streak_days` 按 `delta <= 0` 判违规记录
→ **清白计时器被凭空掐断**。

**真库上实测到**：某账号唯一一条流水就是 `login.daily / delta=0 / at_boundary`，
`streak_days` 返回 **0 而不是 3650**。

**修法**：只有**扣分**规则才写边界流水。扣分侧需要它（0 分用户持续违规时靠它重置恢复
计时器），加分侧没有对应机制、写了纯属噪音。

## 五、生成审计 —— 整条链从零做

### 为什么不能拿 `security_events` 兼职

安全事件表的队列**有上限、满了丢最旧的**。一次生成写一条事件的话，
正常使用几小时就能把队列刷满 —— **等于让 AI 用量把真正的攻击记录挤掉**。

### ⚠️ 这里刻意**不用** `security_log` 那套队列

跟 `security_log` 不同，审计走**直接 await**。三个理由：

1. **调用频率差着量级** —— `security_log` 挂在中间件上、每个 HTTP 请求都走；
   审计是每次生成一条，而生成本身要等模型几秒，多一次 ~50ms 的 INSERT 占比不到 1%
2. **排队会丢数据，而审计最怕丢** —— 丢的就是「这段用量记录没了」，
   统计失真**比没有更难查**
3. **调用方本来就在等** —— 直接写能让「返回值已经拿到」和「审计已经落库」同一时刻成立

provider_error / empty_output / too_short / json_parse_failed）·

## 教训

1. **🎯「页面是空的」和「页面坏了」长得一模一样。**
   这次四条拦路的里，「前端过一遍」原以为只是确认空状态渲染，
   实际挖出四个真 bug。**打开看一眼**的成本，远小于「等用户报障」。

2. **🎯 手工拼 URL 有两张脸：`+` 和 `%`。**
   一个是时间戳里的时区偏移变成空格，一个是通配符 `%` 变成非法转义。
   **都只有真库才暴露** —— 假后端不做真实的 URL 解析。
   规矩：**查询条件一律走 `params=`**；确需手工拼时，先 `quote()` 再把 `%` 通配符换成 `*`。

3. **🎯「没取到」和「取到了空值」长得一模一样 —— 这个形状又出现了。**
   `count=exact` 写错位置 → 400 → `total = 0`；搜索 500 → 返回空列表。
   **读接口把非 200 降级成空数据，是这类 bug 最好的藏身处。**

4. **🎯 验证清理，必须比对快照，不能只看「删了几行」。**
   这次漏删一行，是因为 id 列表来自一次**失败的空查询** ——
