### LoginGate 的设计取舍

一开始写成「页面里写 `v-if="!authStore.isLoggedIn"`」，那需要每个页面都 import authStore，
31 个页面就是 31 处易错点。改成**组件内部自己判断**后，每页只需一行、且无需 import。
`z-index` 设成 9999 —— 设置页里有个 999 的弹窗遮罩，900 会被盖住。

### 游客能真正用起来的（后端本来就是免登录接口）

学科考纲浏览 → 考纲详情 → 真题套卷列表 → 卷子详情 → **做题交卷**，加使用指引 / 开源文档 / 工具箱。
这条主线正好对应指引里「先通过完整页面展示小程序的功能」。

### 需登录页面为什么用占位层而不是弹窗

指引三要求「用户拒绝授权某权限，可暂停提供和该权限有关的功能，但**和该权限无关的功能应该可让用户继续使用**」。
整页需要登录的页面直接弹窗 = 打断体验；给一个带「先逛逛别的」出口的整页占位才对。

## 三、登录流程改造（用户要求）

用户原话：「微信登录是要询问是否有网页版账号，没有就生成了账号，按网页版的生成要求来，
邮箱，验证什么的，然后有的话就绑定」。

改后的四步流程：

```
[微信一键登录]
      ↓ 后端判断是否绑定过
      ├─ 绑定过 ──────────────→ 直接登录
      └─ 没绑定过
            ↓
   「你已经有基智账号了吗？」
      ├─ 已有，去绑定 → 邮箱/用户名 + 密码 ──→ POST /auth/wx-bind
      └─ 没有，创建新账号 → 邮箱 + 验证码 + 密码 + 昵称
                              ├─ POST /auth/send-code  （60 秒倒计时）
                              ├─ POST /auth/register
                              └─ POST /auth/wx-bind    → 绑定并登录
```

### 关键发现：改造前**没有任何人能注册**

`POST /auth/wx-login` 对没绑定过的微信只返回 `need_bind`，要求输入**网页端的邮箱/用户名 + 密码**；
`POST /auth/register` 后端虽然存在，**小程序里从来没接**。

后果：**没有任何基智网页账号的人（包括审核员）根本登不进去** —— 点「微信一键登录」会卡在一个
他无法完成的绑定表单上。这极可能成为下一条驳回理由。

### 实现细节

- **后端一行没改** —— `/auth/send-code`、`/auth/register`、`/auth/wx-bind` 全是现成的
- **`/auth/register` 不返回 token** —— 所以是「先注册、再用同一套邮箱密码绑定微信」两步
- **`/auth/send-code` 的 email 是 query 参数不是 body** —— 拼在 URL 上
- 边缘情况：注册成功但绑定失败时，提示「账号已创建」并把邮箱密码填好跳到绑定页，
  不让用户以为白注册了

### 顺带确认：网页版扫码登录**已经存在**

`views/Login.vue` 有完整的微信扫码按钮 + 二维码 + 轮询，后端 `/auth/wechat/qrcode`、
`/auth/wechat/poll/{token}`、`/auth/wechat/callback` 也都实现了（走公众号测试号 `wx888fb32157efcaf7`）。
用户以为要新做，实际不用。

## 四、诊断「点击登录失效」

用户报「现在点击登录会失效」。逐个排除：

| 检查 | 结果 |
|---|---|
| `POST https://api.jizhi-learn.com/auth/wx-login`（喂假 code） | ✅ 返回 `微信错误(40029): invalid code` |
| 服务器 `WECHAT_MP_APPID` | ✅ `wx6db1f1a6e3f3969c`，与小程序 manifest 一致 |
| 服务器 `WECHAT_MP_SECRET` | ✅ 已配置 |
| **`http://localhost:8000`** | ❌ **连不上，本地后端没在跑** |
| dev 构建的 BASE_URL | `http://localhost:8000` |
| build 产物的 BASE_URL | `https://api.jizhi-learn.com`（仅此一个，无残留） |
| 开发者工具 `urlCheck` | `false`（不拦请求） |

**结论：后端是健康的。** 那条 `40029` 恰恰是好消息 —— 说明服务器成功连上了微信服务器、
appid/secret 都对，用真实 code 就能换到 openid。

**"失效"的真身大概率是本地后端没起**：跑 `npm run dev:mp-weixin` 时 BASE_URL 指向 localhost，
后端不开则每个请求都失败。跑 build 产物则直连生产，不受影响。

> ⚠️ 真机另有一道坎：`api.jizhi-learn.com` 必须加进 mp 后台的「request 合法域名」。
> 开发者工具不校验，真机直接失败。此事仍挂在待办。

## 教训

1. **`du -sk` 会把每个小文件按块大小向上取整** —— 构建产物用 `du` 量出 1.46 MB，
   实际 `getsize` 累加只有 **1.02 MB**（`static` 365.8 KB 与日志里的 366 KB 完全吻合）。
   差点据此误报「包体积涨了 0.47 MB，不正常」。
2. **扫描脚本第一次就写错了**（字符串字面量没剥）。这次学乖了：**先拿带已知 bug 的备份验证扫描器**，
   确认它真能命中，再信它的「0 处」。
3. **Windows 控制台是 GBK，打印 emoji / 中文会炸**（`UnicodeEncodeError`）——
   09-18 已经踩过一次，这轮又踩了一次。脚本里输出一律用 ASCII 标记（YES/NO）。
