### 讯飞语音客户端重写（`backend/utils/xunfei_client.py`）

- **实测发现老客户端是坏的**：TTS 报 `10106 invalid X-Param`（旧版签名格式，讯飞网关已升级）、ASR 报「未知错误」。**这意味着 08-23 的 API 模型中心「语音预览」实际一直 500 不可用**
- 多轮实验（HTTP 老接口 6+ 变体全部失败，错误码 10105/10106/10107）→ 结论：老版 HTTP 接口对该 appid 已不可用，按官方现行 **WebSocket v2** 重写：
  - TTS：`wss://tts-api.xfyun.cn/v2/tts`（lame→mp3，短文本单帧 status=2，长文本分帧）
  - ASR：`wss://iat-api.xfyun.cn/v2/iat`（raw 16k PCM 40ms/帧，rpl 渐进帧拼接，status=2 收尾；wav 容器自动转 16k 单声道）
  - 鉴权：hmac-sha256（host/date/GET request-line）→ authorization 字符串（`api_key="...", algorithm=...` 形式，**不是 JSON**）base64 后走 URL query；卡住两次的坑：① authorization 写成 JSON 报「host not used for signature creation」② 首帧发空 text 报「text is null」
- **验证**：TTS 出 mp3（22KB/9.7KB 两音色）；ASR 用 Windows SAPI 生成的真实中文语音识别出「你好我是小鸡」（机器音把「基」听成「鸡」属音频质量，链路正确）；HTTP 端点端到端 200（后端 --reload 自动生效）

### Bug 修复（用户真机实测发现）
- **现象**：点麦克风录音后报 `语音识别失败: InvalidCharacterError: Failed to execute 'btoa' ... outside of the Latin1 range`（blobToPcm16kBase64）
- **根因**：Int16Array 负样本值经 `String.fromCharCode` 变成 >0xFF 的双字节字符，`btoa` 只接受 Latin1 范围
- **修复**：改用 `Uint8Array(pcm.buffer)` 小端字节流（值域 0-255）分块拼二进制串再 btoa；Node 往返验证（含 ±32768 极值）无损；vite build 通过
- 说明：报错说明录音→解码→重采样全链路已通，只卡在最后的编码一步

## 语音输入升级：录音转写 → 实时听写（同日第三轮）

### 背景
用户提出「能不能不用录音，直接转文字」——要边说话边出字的实时听写，而不是录完再识别。

### 方案
讯飞 iat 本就是流式协议，改造链路为：**麦克风 PCM 实时流 → 后端 WS 中转 → 讯飞 iat 流式识别 → 逐字回传填输入框**。

| 文件 | 改动 |
|---|---|
| `backend/routers/xiaoji.py` | 🆕 `WS /xiaoji/asr-ws` 中转端点：浏览器 WS 收 PCM 帧（status 0/2）→ 转发讯飞 iat WS → rpl 帧实时回传 `{"text": 累计文本, "done": false}`，`data.status=2` 收尾帧回传 `done: true`；浏览器断开即停 relay，正常收尾最多等 8s |
| `components/XiaojiCall.vue` | MediaRecorder 整段录音流程整体替换：AudioContext(16k) + ScriptProcessor 持续取 PCM → base64 → WS 发送；rpl 结果实时回填输入框（原有文本 + 识别文本拼接）；点停止发 status=2 收尾；4s 兜底关闭；采样率非 16k 时线性降采样兜底 |
| `api/xiaoji.js` | 移除不再使用的一次性 `xiaojiAsr` 封装（死代码清理） |

### 排障记录（两个中转时序 bug）
1. `asyncio.wait(FIRST_COMPLETED)`：浏览器发完 status=2 后 forward 先完成，relay 被立即取消，讯飞最终结果被掐断 → 改为先 await forward，浏览器断开则停 relay，否则等 relay 最多 8s
2. 最终帧不发 done：讯飞收尾帧是 `pgs=apd, status=2`（空文本），只认 rpl 导致 done 永不触发 → 改为 `data.status==2` 判定收尾，回传最后累计文本 + done

### 验证
- Python 模拟浏览器流式客户端实测：5 帧渐进部分结果（你好 → 你好我是小鸡）实时到达 + 最终帧 `done: true` 正常收尾
- vite build 通过（1.36s）；py_compile 通过
- 遗留：浏览器真机点按体验（权限/实时出字节奏）待用户确认

### 交互修正：说完自动结束（用户反馈两轮）
- **反馈 1**：「停顿一下再说话就没有加载」——实测复现：讯飞 vad_eos=3s 静音断句后，新段落结果文本**重置**（第二段 rpl 从「你好」重新开始），前端替换导致累计文本丢失、且流程不停
- **反馈 2**：「再次点击才结束录音，所以不对」——要说完自动结束
- **踩坑**：曾以为 rpl = 断句信号（实测发现连续说话期间每个 rpl 都是渐进更新：你好 → 你好我 → …），把 rpl 当 done 会导致提前收尾只识别出开头两个字
- **最终方案**：
  - 后端：rpl/apd 帧一律作为渐进结果回传 `{text, done: false}`；只有 `data.status==2`（客户端收尾）回传 done；`vad_eos` 3s → **10s**（服务端不抢先断句，避免文本重置）
  - 前端：ScriptProcessor 每帧算 RMS，**连续静音 ~2.5s（40 帧×64ms）自动发 status=2 收尾**，关麦释放；说话中点击仍可手动提前结束
- **验证**：模拟实测——渐进帧完整递增（你 → 你好 → … → 你好我是小鸡）+ 最终帧 done 带完整文本；vite build / py_compile 通过

## 小基聊天流式输出 + 句子级语音播报（同日第四轮：解决延迟）

### 背景
用户反馈两点：① 语音播报延迟很大 ② 小基回复不是流式输出（整段一次性出现）。

### 根因
- 聊天：`/community/xiaoji/chat` 用豆包 VolcClient 非流式，全文合成完一次性返回
- 语音：整段回复一次性送讯飞合成，合成完才开始播放（长回复首声延迟 = LLM 全文耗时 + 整段 TTS 耗时）

### 改动
| 文件 | 改动 |
|---|---|
| `routers/community/xiaoji.py` | 抽公共函数 `_build_xiaoji_chat_messages`（昵称 + 配置名称/语气风格 + 10 条上下文）和 `_save_xiaoji_message`；`/chat` 豆包 → DeepSeek `call_llm`（与平台主模型一致）；🆕 `/xiaoji/chat-stream` SSE 流式端点（`call_llm_stream` 逐片 yield + 完成后落库 + 异常兜底文案）；profile 查询加固（非 200/非列表不再 KeyError） |
| `components/XiaojiCall.vue` | ① 聊天改流式：fetch + reader 逐字更新占位气泡（TextDecoder stream 模式）② 播报改**句子级队列**：流式文本按 `。！？；!?;\n` 边界切分，成句即入队讯飞合成、逐句播放——首句声音随文字同步出来，不用等全文；短句合成 0.4s 级；缓存按句子粒度复用；整段场景（问候/评价/识图回复）同样走队列；关播报清队列 |

### 排障记录
- 500：测试用非 UUID 用户 id 触发 PostgREST 400 → 原代码 `json()[0]` KeyError（真实用户不受影响，顺手加固）
- 兜底文案：`call_llm_stream` 产出的是**文本片段**（非 OpenAI 对象），端点里按 `chunk.choices[0].delta.content` 取字段导致流内异常 → 改为直接拼接 yield

### 验证
- 实测流式端点：200，首字节 1.73s、总耗时 5.98s、266 字完整回复（人设/语气风格注入正常）；vite build / py_compile 通过
- 预期体验：文字逐字出，首句语音在首句文字后 ~0.5s 跟上；总延迟从「全文 + 整段合成」降到「首句 + 单句合成」
- 遗留：浏览器真机体验待用户确认；讯飞 TTS 逐句调用频率升高，缓存已缓解（重复句子不再消耗额度）

### 停止朗读按钮 + 名称显示 + 设置盘点（同日第五轮）
- **停止朗读（豆包式）**：输入工具栏在播报期间出现红色 ■ 按钮（脉冲动画），点击立即停当前播放 + 清空合成队列 + 丢弃本段剩余句子；只停本次朗读，语音播报开关不受影响；下次回复/问候自动恢复；关播报开关同样置停止标记（避免在合成途中的句子漏播）
