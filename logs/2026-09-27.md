## 二、#1 / #4 导出失败 —— 端到端复现

### 根因

`html2canvas@1.4.1` 的颜色解析器：

```js
// node_modules/html2canvas/dist/html2canvas.js:1837
var SUPPORTED_COLOR_FUNCTIONS = { hsl, hsla, rgb, rgba };   // ← 只有这四个
// :1726
throw new Error("Attempting to parse an unsupported color function \"" + value.name + "\"");
```

而 **Chrome 在 computed value 阶段就把 `color-mix()` 算掉了**，序列化成：

```
color(srgb 0.62549 0.809804 1)          ← 函数名是 "color"，不在表里 → throw
```

实测 `getComputedStyle` 的四种位置**全都是这个形式**：`color` / `backgroundColor` /
`borderColor` / 连渐变里的色标（`linear-gradient(color(srgb …) 0%, rgb(…) 100%)`）。

范围：**网页端 `color-mix()` 用了 1124 处、74 个文件**；三个导出组件自身就有
（资料卡 20、评估报告 19、评估表 20）。

### 复现（headless Chrome，真实 html2canvas）

```
RESULT: THREW — Error: Attempting to parse an unsupported color function "color"
```

### 为什么用户只看到「导出失败」四个字

```js
// CommunityProfileCard.vue:687-707
try { await doExport(cardRef.value, 'pdf') }
catch { ElMessage.error('导出失败') }      // ← 异常整个吞掉，连 console 都不打
```

预览弹窗那两个入口（`:709` / `:713`）**连 try/catch 都没有**，点了完全没反应。

### 修法：不加依赖，把已算好的颜色降级

关键洞察：**混色数学不用重算**——浏览器已经算完了，只需把 `color(srgb r g b / a)`
转成 `rgba(R,G,B,A)` 写成 inline style（inline 优先级最高，会带进 html2canvas 的 clone）。

新增 `frontend/src/utils/exportColor.js`：`normalizeModernColors(el)` +
`withNormalizedColors(el, fn)`（包装版，让调用点改动面最小）。

**这和项目已有约定是一致的**：`stores/theme.js:74` 的 `withAlpha()` 注释写着
「ECharts canvas 不认 CSS var()/color-mix——品牌色半透明需 JS 解析成 rgba」。
同一次主题改版里 **ECharts 适配了、html2canvas 漏了**。所以补共用 util 比引新库更贴既有架构。

### ⚠️ 实现时自己踩的一个坑

第一版是**边读 computed style 边写 inline style**，交替进行会「写一次 → 下次读强制重排」，
资料卡有几百个节点，会明显卡。改成**两趟**：先全读收集、再全写。各只触发一次布局。

### 验证（加载真实文件跑，不是复制逻辑）

```
step2  基线 computed 值   = color(srgb 0.62549 0.809804 1)
step3  不打补丁            → THREW: Attempting to parse an unsupported color function "color"
step4  打了补丁            → rgb(159, 207, 255)
step5  实际渲染像素        = 159,207,255,255      ← 与手算逐位吻合
step8  还原后              = color(srgb 0.62549 0.809804 1)
step9  残留 inline style   = (none)
```

手算对照：`#409EFF` 50% 混白 = R:0.5×64+0.5×255=**159.5→159**、G:0.5×158+0.5×255=**206.5→207**、B:255 ✓

测试环境本身也踩了一个坑：Windows 上 Python `http.server` 从注册表读 MIME，
`.js` 被判成 **`text/plain`** → ES 模块直接拒绝加载（`Failed to fetch dynamically
imported module`）。换了个强制 MIME 的小服务器才跑通。

### 顺带修的两个连带问题

- `EvaluationReport.vue:520` / `EvaluationTable.vue:347` 一字不差的
  `if (!reportContentRef.value) return`，而 `pdfExporting` 在 return **之后**才置位。
  导出根节点只存在于 `v-else` 分支，**报告加载中点击什么都不会发生**——没 toast、
  没 loading、没报错。这是与「导出失败」**不同的症状**，容易被当成第 9 个 bug 去查。
  改为 `ElMessage.warning('报告还在加载，请稍候再试')`。
- 预览入口无 try/catch：**未改**（改动面大，且不在用户报的症状里）。

## 三、#5 奖励成就领取 —— 执行复现

### 根因

后端三个 claim 接口**直接调用**了同样带 `Depends(get_current_user)` 的路由函数：

```python
async def get_task_progress(user_id: str, current_user: str = Depends(get_current_user)):
    verify_user_match(user_id, current_user)

async def claim_task(req, current_user: str = Depends(get_current_user)):
    verify_user_match(req.user_id, current_user)          # ← 这行是通过的
    progress_data = await get_task_progress(req.user_id)  # ← current_user 落到 Depends 默认值
```

`current_user` 变成 `Depends` 实例 → `verify_user_match` 比对
`param_user_id != token_user_id` **必然不等** → **一律 403「无权操作其他用户的数据」**。

子代理用真实模块执行复现：`asyncio.run(c.get_task_progress('probe-user-000'))`
→ `HTTPException 403`。

### 一个不可逆的副作用（**至今未处理**）

- `claim_task` 第 448 行立刻 403 → **什么都没写**
- `claim_achievement` 的 403 发生在第 409 行，**晚于第 405 行写 `user_achievements`**
  → **成就行已落库但积分永不发放**，重试命中「成就已领取」(200 + success:false)
  → **永久卡死**
- `claim_bonus` 同型（先写 `user_task_claims`）

### 修法：拆「路由壳 + 核心逻辑」

新增 `_apply_user_stats(...)` 与 `_compute_task_progress(user_id)`，**不带 Depends、
不自行鉴权**（docstring 里写明调用方必须先 `verify_user_match`）；
路由函数保留鉴权后转调。4 处直调点全部改指核心函数。

### ⚠️ 扫描器自己先写错了（又是那个老坑）

第一版扫描脚本报「**0 处直调**」——不可信。原因是正则用了 `[^)]*`，
**处理不了 `Depends(get_current_user)` 里的嵌套括号**。修好正则后扫出 **4 处**：

```
routers/career.py:409 / :448 / :500 / :539
```

**子代理报的是 3 处，漏了 `:500`。** 这正是 09-18 记过的
「报『通过/失败』之前，先确认校验器本身是对的」——**第二次踩**。

### 验证

```
py_compile                                    OK
全后端扫描   guarded=130  direct-calls=0       PASS
直调核心函数  → 返回 {'error':…}，不再抛 403    ✓（已越过鉴权、真的发起网络请求）
传入不匹配 user_id → 仍然 403                  ✓（安全没被改掉）
```

## 四、#3 自营视频 —— 命名空间错配

### 根因

```js
// frontend/src/views/DoQuestion.vue:764
const subject = q.category || '通用'
```

`knowledge_key` 的形式是 **`f"{subject}:{sha1(知识点)[:12]}"`** ——
**前缀一变，整个键就变了**。实测对比：

```
related?knowledge_key=ncre2-office:5ca68d755414&subject=ncre2-office  → 4 条
related?knowledge_key=excel:5ca68d755414&subject=excel                → 0 条
                              ^^^^^^^^^^^^ 同一个哈希
```

**第二个致命处**：`video_gen.py` 的兜底写在 `if subject:` 分支里，
而前端**永远传非空 subject** → 55 分的全局兜底**永远走不到** → 结果必然空列表。

前端拿到 0 条后显示「写讲稿」占位并轮询 5×8s = 40 秒，而实测生成一条视频要 **4 分 14 秒**
→ 轮询必然耗尽、列表为空、整块 `v-if` 为假直接消失 = 用户看到的「一直加载不出来」。

**附带后果**：`ensure` 每次都 miss，**每次答错都新建一条排产**，真跑千问 TTS 产生费用。

### 修法（两处）

1. 前端 `DoQuestion.vue:764` → `q.syllabus_id || q.category || '通用'`
   （题目对象**本来就带 `syllabus_id`**，同文件 `:560` 一直在用，只是没拿它当视频库 subject）
2. 后端 `related_videos` 兜底重写为**三档降级**：

```
90 = 只比对「知识点哈希」（跨命名空间，前缀不参与）
70 = 同学科
55 = 全局
```

### 验证（喂入采集到的 32 条真实视频行）

| 用例 | 修复前 | 修复后 |
|---|---|---|
| `excel:5ca68d755414` / subject=excel | **0 条** | **6 条**，首条 `match=90 subject='ncre2-office'` ← 靠哈希档命中 |
| `ncre2-office:5ca68d755414` | 6 条 | 6 条，`exact=1` `match=100` ← **原行为未被破坏** |
| 完全不存在的 key | 0 条 | 落到 55 分全局兜底 ← **兜底终于可达** |

### 顺带确认：音轨本身没问题

调查组无法验证 Supabase 音频 URL（沙箱网络不通），我这边有外网，实测：

```
HTTP/1.1 200 OK   Content-Type: audio/mpeg   Content-Length: 1448731
Access-Control-Allow-Origin: *   Accept-Ranges: bytes
实拉前 4KB: HTTP 206   magic bytes = ID3\x03   → 真 MP3
```

**结论：音轨在公网是公开可取的真实音频，桶策略和 CORS 都正常。**
「大陆不可达」这个第二成因可以排除。

**真缺陷**：

- `auth.py:1034` PATCH `profiles` **用 anon key**（`SUPABASE_SERVICE_ROLE_KEY` 存在却没用），
  **`patch_res` 赋值后从不检查状态码**。而 UPDATE 被 RLS 拦是

- 写 profiles 换 `get_supabase_service_headers()` + 状态码判断 + **回读校验**
  （写完再查一次，`wechat_openid != req.openid` 就抛 502）——RLS 静默 0 行只有回读能发现
- 返回值改为**回显库里的值**
- 限流改两级：按「IP + 登录账号」5 次/60 秒（**与本文件 `/login:30` 同一套写法**，
  `wx-bind` 原来是这里唯一的例外）+ 按 IP 总量 20 次/60 秒防换号扫

`service_headers` 拼的是 `Bearer {SUPABASE_SERVICE_ROLE_KEY}`，
**生产若没配这个 key，会拼出 `Bearer None` → 请求直接 401，比改之前更糟**。

特意加了一道显式闸门：key 为空时直接抛 500 并打日志。
**报错好过原来的静默假成功。**
本地已核验：`SUPABASE_KEY` role=`anon`、`SUPABASE_SERVICE_ROLE_KEY` role=`service_role`，
同 ref `tfpdghlhqlmqhplvkank`。

### 排查（关键一步：同 IP 换 SNI）

| 测试 | 结果 |
|---|---|
| 本机 8000 端口 | 在监听，`/openapi.json` **200** —— 后端活着 |
| 那批接口**不带 token** | **401** —— 接口本身没坏，503 是中间件加的 |
| `…supabase.co/auth/v1/user` | TLS 握手被 **reset**（`time_appconnect`=0） |

→ **按 SNI 定向阻断，不是 IP 被封，也不是 Cloudflare 的问题。**

**Chrome 走 HTTP/3（QUIC），QUIC 把 SNI 也加密了**，中间设备看不见域名。
curl / Python(httpx) 走 TCP TLS，SNI 明文 → 一眼认出来 → 掐断。

「浏览器能开、命令行不能」不是矛盾，**这个差异本身就是线索**。
