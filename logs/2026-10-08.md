### 2.1 新增 `utils/notify_events.py`（跨文件复用的快捷函数）

设计契约是「一个点 = 注册表一行 + 事件处一次 `notify()`」，多数点确实就地写 4 行就够
（`community/posts.py` 的 `_notify_post_author` 就是范本）。

但有两个是**同一事件、多个入口**：

- `learning.plan_generated` —— 建计划有**三条互不共用代码**的路径
  （自定义计划 / 摸底诊断 / 真题答卷）
- `learning.mastery_jump` · `learning.weak_alert` —— 掌握度有**两个写入点**
  （学科计划的 EWMA、AI 生成题的 LLM 直接给分）

同一段 `notify()` 抄五遍，改一处漏四处，所以抽出来。**只放 ≥2 个文件要用的**，
单文件用的仍旧就地写。文件头写明了这个边界。

### 2.2 注册表改了一处：`social.rank_pass` → `aggregate=True`

不是美化，是**不改就报错**：`notify()` 用「先 INSERT，撞部分唯一索引(409) 再改走 UPDATE」
实现聚合，而回退分支的条件是 `409 and s["aggregate"] and source_id`。
`rank_pass` 原本 `aggregate=False`，我又按天传了 `source_id` ——
第二次超过好友时必然 409，且**不会走聚合分支，直接抛 `NotifyError`**。

语义上聚合也是对的：一次涨分可能同时超过好几位好友，紧接着几次涨分还会再超过人。

### 2.3 好友榜超越怎么判的

判定就一句：**他的分原本在你之上（含持平），现在被你够到或反超了**
—— `old_points < 他的分 <= new_points`。

这个区间是精确的。只拿 `new_points` 跟好友比大小，会把「你早就超过的人」每次涨分重报一遍。

代价：**每次涨分多查两次库**（friendships + user_stats）。所以加了 `points_change > 0`
的前置判断，且只在 `_apply_user_stats` 里挂 —— 它由领取接口和 `/stats/update` 调用，
**不在 `record_action` 的埋点路径上**（那条路每答一道题走一次，挂那儿就废了）。

## 教训

1. **「接完」这个词要先拆。** 用户以为「注册了 66 个，剩 40 个没接，接完就完事」；
   量出来是「33 个里 14 个没有事件源」。**注册 ≠ 可接** ——
   注册表只声明「这个点存在」，不保证「触发它的事存在」。
   动手前先按「有没有事件源」分一遍，能省掉一次「怎么接不完」的对话。
2. **注册表里的 `aggregate` 不是装饰。** 不聚合又传 `source_id`，
   第二次就撞部分唯一索引，而且**不会走聚合回退分支**（那个分支要求 `aggregate=True`），
   直接抛 `NotifyError`。**给一个点加 `source_id` 之前，先看它是不是 aggregate。**
3. **静默失败的第四个变体：失败返回 `None` 不抛。**
   `_save_paper_record`（`exam_papers.py:630`）落库失败只 `print` 并 `return None`。
   接通知时必须 `if record_id:` —— 不判就会为一份**没存下来的卷子**发「批改完成」。
   前三个变体是：写不存在的列、权限 42501、非 200 降级成空。**共同点还是「返回值没人看」。**
4. **阈值这种东西，不该由我发明。** `JUMP_DELTA` / `WEAK_ALERT_AT` 是我拍的 ——
   注册表没写、设计文档没写。这次至少把它们**收在两个常量里 + 在日志里点名**，
   而不是散在判定式里假装它本来就该是 20。**（10-07 教训 4 的同一个病，这次按住了。）**
5. **重构前把要碰的地方读透，回报率很高**（10-07 说过一次，今天又验证）：
   三个既有缺陷（磨合引擎两条规则恒不触发、subject_plans 无进度、删好友单向）
   都是**为了接线去读代码时撞见的**，没有一个是这轮引入的。

### 1.1 `notify_broadcast()` —— 第一个也是唯一一个绕开 `notify()` 的写入口

公告是**推 vs 拉**的冲突：它原本走 `system_announcements` 表 + `/announcements/active`（拉），
而消息中心是推。逐人走 `notify()` 是 **2N 次 HTTP 往返**（每人还要查一次设置），
几百人就能把管理员的「发布」按钮卡到超时。

所以开了个受控口子：数组插入一次写一批，开关改成**查退订名单**（反向查一次）。
文件头写明了这是第二个写入口以及为什么，**除它之外任何写入都必须走 `notify()`**。

新加了两条回归测试，其中一条**第一版就抓到了我自己的错**：假 HTTP 客户端把
`select=id` 回成了裸字符串，而 PostgREST 回的是 `[{"id": ...}]`。
（桩和实现都是我写的，一起错的时候测试是绿的 —— 这次是运气好。）

### 1.2 🎯 一个反复咬人的坑：非聚合类型 + `source_id`

未读聚合的部分唯一索引建在 `(user_id, type, source_id) WHERE is_read=false` 上，
**不看 `aggregate`**。给**非聚合**类型传 `source_id`，第二次撞索引时因为 `aggregate=false`
**不走聚合回退、直接抛 `NotifyError`**。

这轮有 **三处**差点踩上，各用不同办法绕开：

| 消息点 | 办法 |
|---|---|
| `admin.new_report` | `source_id` 传**每份举报各不相同的 id** → 永远撞不上 |
| `admin.content_review` | **不传 `source_id`** —— 同一个视频可以「被驳回 → 重新申请」，传了会让管理员漏掉重审 |
| `learning.mistake_conquered` | 改成 `aggregate=True` + 按天取 `source_id`（用户定的按天聚合） |

## 三、每日学习推荐（三合一）

### 3.1 先量：它根本是断的

用户说「小基推荐其实就是学习推荐，你要做好这里」。量下来是这样：

| 现状 | 问题 |
|---|---|
| `/xiaoji/daily` 读 `notifications` 里最新一条 `learning.daily_rec` | 卡片和消息中心**读的是同一行数据**（数据层早就是同一个东西） |
| 后端只产一段 120 字 LLM 文字 | `daily_generator.py:281` 留着 TODO：payload 要装三块 |
| 卡片按钮跳 `/resource-lib` | ⚠️ **按钮是坏的**，见下 |
| 消息中心那个三合一面板 | ⚠️ **是空壳** |

**两处「看着没问题」的坏链：**

1. **卡片按钮点了没反应**。它读 `daily.recommendation.action_link`。
   ⚠️ 我一开始判断「`action_link` 不是 notifications 表的列」——**这个判断是错的**，
   实测那四列（`summary` / `image_url` / `action_label` / `action_link`）**建表时就有**。
   真相是：**`notify()` 从不写它们**（全站统一走 `link`），所以每行都是空 → 前端拿不到地址。
   结论一样（按钮是坏的），但原因不同。**我在四处注释里写错了，已全部订正。**
2. **消息中心的三合一面板是空壳**：「提交这 N 题」只做了 `recDone.questions = true`，
   **零 API 调用**，连它上面那句「作答会写入你的做题记录与错题本」都是假的。

### 3.2 做成什么

**用户拍板**：独立全屏页 `/daily-learn`，**首页卡片和消息中心那条进的是同一个页面**。
（设计文档 §六 原本写的是「详情里可以直接做，不是跳出去做」，本次**按用户口径改掉了**，
设计文档已同步订正。）

- **payload**：`content`（标题/kp_id/分钟/依据，正文按需生成）+ `questions` + `video` + `progress`
- ⚠️ **`syllabus_id` 是补的**：§六 给的 schema 漏了它。题库 18,711 题里 **497 个 id 横跨多库**，
  做题端靠它定位题目，不带就会跨库猜 —— **拿 A 科目的题判 B 科目的分**。
- **正文不在发送时生成**（太贵），首次打开学习页时按需生成并写回 payload（幂等）。
  每日推荐**没有任务行**可当缓存载体（学科计划缓存在 `plan_daily_tasks.learning_content`、
  自定义计划在 `learning_tasks.lesson_content`），只能回写进 payload 自己。
- **视频只做命中复用**：新增 `video_gen.find_ready_video()`（**纯只读**）。
  ⚠️ **绝不能用 `ensure_videos()` 代替** —— 那是「查 + 补产」二合一，查不到就插行排产。

### 3.3 顺手抽掉的重复

- `routers/video.py` 里内联的分层打分（120/100/80/60/+15）→ `services/kp_questions.py`，两处共用
- `video_gen` 里跨命名哈希匹配**原本在 `related_videos` 和 `/lib/status` 各写一份** → 抽出 `_split_kp_hash`
- `getStem` / `getOptions` 原本是 `SubjectPractice.vue` 的**局部函数** → 抽到 `utils/questionLabels.js`
  （否则我的新页面就是第 3 份）

## 四、定时 + 设置生效 + 手动按键

用户：「要做定时，而且要做好设置是有效的，也可以加一个按键……检测到今日已生成就不用在定时再次生成……
生成有两个逻辑。时间先设置为早上 8 点。」

**「两个逻辑」= 每日学习推荐 + 每日总结**（设计文档 §十：「加两个独立项」）。

| 项 | 做法 |
|---|---|
| **调度** | `services/daily_scheduler.py` **每 10 分钟轮询**。为什么不是「每天 8 点跑一次」：发送时间是**每用户自己设的**，全局定时器表达不了。用 `>=` 而非 `==`，服务器重启期间错过的时间点下一轮能补上 |
| **设置真的生效** | `daily_generator.deliver()` 统一读四个键。§十 原话「后端必须真的读这些开关（现在没有任何代码读它们）」——这轮兑现 |
| **默认 8 点** | 收进 `utils/notification.DEFAULT_SETTINGS` |
| **按天去重** | `has_today()` **生成之前先查库**：既省 LLM，又避开「非聚合类型撞唯一索引直接抛」 |
| **手动按键** | `POST /daily-learn/generate`，放首页推荐卡**空态**里。`force` 只忽略时间、**去重照旧**（点几次都安全） |

⚠️ **默认值原本有两份**：设置页硬编码了 `{"daily_rec_time": "08:00", ...}`，
而调度器读的 `DEFAULT_SETTINGS` 里**没有这两个键** ——
结果是**设置页显示 08:00、后台按「随时发」跑**。现在只有一份。

### 5.1 🚨 `notifications.type` 上的陈年 CHECK —— 消息中心**一条都发不出来**

```
POST /rest/v1/notifications → 400  {"code":"23514"}
```

`23514` = **check_violation**（外键是 23503、非空是 23502）。

只读排查：`notifications` 全表 5 行，`type` **只有 `chat` / `system` 两个无点号的老值**；
10-07 引入的 66 个新类型全是 `组.动作` 形式。**建表时（早于本仓库所有迁移文件）
按当时的类型加过一个白名单 CHECK。**

**也就是说：10-07 的 66 个消息点、之后所有接线，在真实库上从来没成功发出过一条通知。**

产出 `sql/notifications_drop_stale_type_check.sql`（先打印现有 CHECK 再删，
只删提到 `type`/`group_key` 的，其余保留）。**不补新的白名单** ——
类型合法性由 `notification_registry.spec()` 把关；DB 里再维护一份 = 同一个概念两个副本，
注册表加了 66 个而 DB 白名单没跟着动，正是这次踩的坑。

> ⚠️ **这个脚本我第一版写错了**：要求约束定义里出现 `IN (`，
> 但 PostgreSQL 会把 `type IN ('chat','system')` 规范化成 `type = ANY (ARRAY[...])` ——
> **没有 `IN (`**。结果是「看得见它、却一个都不删」，跑完还是同样的 23514。
> 已改成按列名词边界匹配，并加了「一个都没删就把定义贴出来」的提示。

### 5.2 三个从没暴露过的崩溃/错误（都不是这轮引入的）

1. **`get_user_yesterday_activity()` 直接崩**：
   `sum((sum(s) for s in topic_scores.values()), [])` —— 内层 `sum(s)` 已把分数列表压成 int，
   外层再拿 `[]` 去拼 → `TypeError: can only concatenate list (not "int") to list`。
   本意是拍平。**一旦真推给用户就是 100% 失败。**
2. **时间戳拼进 URL 被解码**：`isoformat()` 带 `+00:00`，裸拼进 query 时 `+` 变成空格 →
   `invalid input syntax for type timestamp: "... 00:00"` → 整个查询 400、活跃用户恒为 0，
   **看起来像「今天没人活跃」**。必须走 `params=` 让 httpx 编码。
   （`agents/tuning.py` 一直是这么写的，我照抄时漏了这一点。）
   ⚠️ 这处**是我新写的代码**引入的 —— 但它能被发现，是因为我按 10-08 上一节的规矩
   写了 WARNING 而不是静默返回空。
3. **`get_active_users()` 三个问题叠加**：查错表（`questions` 当活跃来源）+ 零时间过滤 +
   profiles 硬截断到 100 个（活跃用户一多，后面的静默收不到推荐）。

### 5.3 🎯 约 1/3 的用户会永远收不到推荐

量下来：依据挑出的 topic 来自 **`questions` 表的 AI 生成题 topic**，
而检索匹配的是**题库的 `kp_name`** —— **是两套词汇**。9 个真实 topic 里
**3 个一道题都搜不到**（`Shell编程` / `切片赋值的长度变化影响` / `比较大小`）。

而 `_pick_focus` 只返回 `weak[0]` **一个**。只试第一个的话，
**约 1/3 的用户会永远收不到推荐** —— 正是设计文档那条回落规则想防的同一类病，
只是换了个地方发作。

**修法**：返回**一串候选**，从前往后试到能凑出内容为止。修完三个用户全部拿到完整推荐。

### 5.4 我自己写错的两处（除上面 SQL 那条）

- **`video_library.duration` 不存在** —— 真实列名是 **`audio_duration`**（秒，浮点）。
  查 `duration` 直接 400。是拉一行数据看出来的。
- **卡片把原来的内容挤下去了**。用户原话：「怎么把原来的内容挤下去了，
  应该是在原来的基础上切割三块展示而已吧」。我用「依据」那一行替换了原来那段 120 字正文，
  还顺手把按钮文案从「立即学习」改成了「开始学习」—— **都是多余的改动，已全部还原**，
  「依据」降级成标题的 tooltip。
- **空态与有推荐时的高度不一样**，右栏会跳（用户：「占位变了，这样子不行」）。

## 教训

1. **🎯「编译通过 + 假 HTTP 单测通过」和「能用」之间隔着一整个数据库。**
   今天最大的收获全部来自**真跑**：一个 100% 必崩的 `TypeError`、
   一个「约 1/3 用户永远收不到」的词汇不匹配、一个让**整个消息中心一条都发不出来**的
   CHECK 约束 —— 三个都是静态读码和假桩**不可能发现**的。
   **假桩测的是「我的代码符合我的预期」，不是「它能用」。**
2. **只在成功时写的字段，不能用来推断失败。**（10-01 已有此条，今天换个形式又中：
   `script_text` → 这次是「`action_link` 是空串」被当成「列不存在」。）
   **实测一行数据比读十遍代码有用** —— 那四列我是拉一行才看见的。
3. **错误信息被截断，就会指错方向。** `res.text[:300]` 把
   「Failing row contains (…)」截在半路，我一度在猜是哪一列；
   打全之后一眼看出列布局。
4. **同一个默认值两份实现，UI 和真实行为就会对不上。**
   设置页硬编码 08:00、调度器读的字典里没有 → 「显示 8 点、按随时发」。
   **收成一份**是唯一的解法。
5. **改对了的地方也要回头看一眼。** 我给 `admin.content_review` **不传 `source_id`**
   是个正确决定，但如果当时顺手传了 video_id，「驳回后重新申请」的通知会被唯一索引吃掉 ——
   管理员**永远看不到重审**。**加 `source_id` 之前先问「这个键会不会重复出现」。**
6. **「原来的东西」不要顺手改掉。** 用户两次纠正都在这上面：把正文换成「依据」、
   把按钮文案从「立即学习」改成「开始学习」。**他要的是「在原基础上加三块」，不是重做卡片。**
   （10-07 教训 1「把最近在做的事当成用户要的东西」的同一类病。）
7. **加剧既有问题也是问题。** 空态与有推荐的高度差本来就存在（90px），我把它拉到 130px
   才被看出来。**改一处之前先量一下它现在是多少。**
8. **我自己写的迁移脚本第一版是错的**（`IN (` 那条），而且是「看着没问题」的错法：
   它会打印出目标约束、却一个都不删。**能观察到 ≠ 能生效。**

## 一、先说一件物理上做不到的事

## 二、桌面通知

| **长条，不是宽方块** | 330×90 的方卡 → **620×54 的横条**。关键是**摘要只占一行 + 省略号** |
| **像消息中心的一条一条** | 照 `.mc-card` 做：左侧 3px 竖色条 + 方形图标 + 标题/时间一行 + 摘要一行 |
| **毛玻璃** | 原来写的是 `88% 不透明` —— 那看着就是块实心板。改成 **62% + `blur(30px) saturate(1.7)` + 一道亮边** |
| **覆盖，不是堆积下去** | 见下 |

### 2.3 「覆盖而不是堆积」—— 为此弃用了 `ElNotification`

`ElNotification` **只会往下堆**：一次来三条就往下长三格。用户要的是同一时刻只有一条、新的顶掉旧的、
**总高度恒定**。所以改成**自己渲染**：一个队列，前一条走了才上后一条。

代价：一次来 3 条是**依次播 3 次**（每条 3 秒），不是同时看到 3 个。队列上限 5 条，
超出的合并成「还有 N 条新消息」。

### 2.4 轮询从 **6 个**收成 1 个

改造前 Sidebar / EdgeNavDock / XiaojiCall / MessageCenter **各自** 30 秒轮询同一个
`/messages/badges` —— 首页三个组件同时挂着就是**同页面 3 份重复请求**。
现在抽成 `composables/useNotifications.js`：**一个计时器、一份共享状态**，四个组件都从它读。

⚠️ **另外两个没动**：`CareerSidebar.vue:298` 和 `CommunitySidebar.vue:81` 打的**不是**
`/messages/badges`，而是**旧的 `/community/sidebar-badges`** —— 正是 10-07 要消灭的
「两套算法」源头。**所以学程页和社区页的角标至今仍和消息中心对不上**，那个 bug 只修了一半。
没动的原因：映射不是 1:1（`friendRequestCount` 来自 `friendships` 表、
`career_tasks` 靠 `link` 里有没有 `tasks` 字符串数、旧 `unread_chairs` 是「按发送者去重」），
换了数据源数字本身就会变，而我没法在浏览器里验证那两页。

### 2.5 角标接口加 `latest`

`/messages/badges` 现在顺带返回**最新一条未读**的摘要。前端比对 `latest.id` 变没变就知道
有没有新消息 —— **零新增接口**，常态下每 30 秒仍只有一个轻查询；
只有 `id` 变了才去拉一次列表（那是全行查询，贵得多）。

✅ **真数据验过**：用户 `126dd6ec` 有 3 条未读，返回的 `latest` 正是最新的那条
`daily_summary`（09:18:17），排序正确。

## 三、消息详情：七种形态

### 3.1 用户原话

「每日学习总结太粗糙了，你再好好设计一下，排版也要好。太丑了，每一个消息都要排版好」

### 3.2 量出来的根因（两个，都很具体）

1. **数字埋在散文里。** 后端把总结写成一段 150 字散文：
   「昨天你完成了50道题，这份坚持很棒。整体掌握度9%，说明……」
   —— 而 `50 道题`、`9%`、薄弱点这些**后端本来就精确算出来了**
   （`get_user_yesterday_activity`），却让 LLM 用自然语言复述一遍。既丑，还可能说错。
2. **`.modal-text` 上没有 `white-space`。** 模型写的 `\n\n` **被 HTML 折叠成空格**，
   多段并成一段 —— 推荐那条正文你看到的就是一坨。

### 3.3 做法：不写 66 套模板，归成 7 种形态

关键约束是 10-07 定的「**加一个消息点 = 注册表加一行，前端零改动**」。
66 个点各写一套模板就把这条毁了。所以让**后端从注册表已有的标志推导形态**
（`notification_registry._shape_of`），前端只认形态名：

```
payload_schema == daily_rec     → rec        学习推荐三合一
payload_schema == daily_summary → summary    昨日总结
aggregate                       → actors     聚合「N 人做了某事」
todo                            → todo       待办
group == system                 → notice     账号/处置类正式通知
group == career                 → celebrate  成就/晋升
其余                            → plain      分段正文
```

⚠️ **顺序有意义**：先看 payload，再看 aggregate / todo，最后按大类兜底。
例如 `todo.set_share` 既是 todo 又在 todo 组，应该走 todo 分支。

**实测分布**：`rec 1 · summary 1 · actors 9 · todo 10 · notice 12 · celebrate 9 · plain 23`。
注册表里可以**逐条覆写**（`shape="..."`），某个点想特殊处理不用改前端。

### 3.4 每种形态的排版

| 形态 | 排版 |
|---|---|
| **actors** | 大号数字「3 共 5 条」+ **带头像圆点的名字标签**（改前是一行行灰块和正文混在一起） |
| **todo** | 橙色提示条「**处理完才算已读，看一眼不算**」+ 正文 |
| **notice** | 图标 + 类型名 + 正文 |
| **celebrate** | 居中大徽章（渐变 + 光晕）+ 居中正文 |
| **summary** | 数字卡片（`tabular-nums` 等宽对齐）+ 知识点标签（淡红=需加强 / 淡绿=掌握不错）+ 左侧色条的建议块 + 右对齐鼓励语 |
| **rec** | 三块预览 + 正文 + 通栏「去学习」 |
| **plain** | 分段正文兜底 |

### 3.5 后端：总结改成结构化

数字和知识点由**后端原样带入**，LLM **只写三段文字**（点评 / 建议 / 鼓励）。
⚠️ **LLM 挂了也不丢整条** —— 退回确定性文案（`_fallback_note` / `_fallback_suggestion`），
**数字始终是真数据**。

✅ 实测通过（真实用户 + 真实 LLM 调用）：
```
50 道题 · 掌握度 9%
需要加强：[Shell编程] [文件操作] [切片赋值的长度变化影响]
点评：题量到位但掌握度偏低，说明当前以接触新知识为主，尚未形成稳定理解。
建议：今天用10分钟手写一遍Shell脚本和切片赋值示例，边写边标注长度变化。
鼓励：刚开始都这样，把每个小问题弄懂就是进步。
```

### 3.6 删掉不该给用户看的

用户：「每条消息的下面有个类型，去向，规则，这些当然不需要的，消息只需要给有需要的」

| 位置 | 删掉的东西 |
|---|---|
| 详情弹层底部 | 「这条消息 / 类型 / 点击去向 / 已读规则」整块 |
| 详情弹层顶部 | 「· 组内第 1/13 个」—— 10-07 验配色派生时留下的 |
| **列表每行下面** | **原始类型键**（`learning.daily_rec` 这种） |

连带清掉死代码：`readRule` computed、`typeMeta` 导入、`.kv` / `.type-key` / `.actor-row` / `.modal-sec` 四条 CSS。

顺带：「标记已读」按钮改成**只在未读时出现** —— `markRead()` 第一行就是 `if (m.is_read) return`，
已读时点了什么都不会发生，摆着是死的。

## 教训

1. **🎯「构建通过」和「能用」之间还隔着一层。** `loadBadge` 那个错构建**完全抓不到** ——
   而它会让消息中心**一打开就崩**。**得为「构建抓不到的东西」单独写检查**
   （今天就是一个脚本：模板调用的函数 vs 脚本里的定义）。
2. **同一个默认值/规则两份实现，迟早在你没看的地方分叉。**（今天第三次中：
   `loadBadge` 删了调用没删、`DEFAULT_SETTINGS` 的时间键、这次的 `canDelete`。）
3. **用户连着提的三条视觉要求，全部指向同一个毛病：我在"能显示"就收手了。**
   长条/毛玻璃/覆盖不堆积 —— 都不是功能问题，是**我没把「好不好看」当成验收标准**。
4. **「不好看」要拆成可执行的点。** 用户说「太粗糙」，量下来是两条很具体的根因
   （数字埋在散文里、CSS 少了 `white-space` 把分段折叠了）。
   **先量再改**这条老规矩，在排版上一样成立。
5. **形态比模板省事，而且不破坏契约。** 66 个消息点各写一套模板 = 毁掉「加消息点前端零改动」；
   归成 7 种由标志推导的形态 = 两边都保住。**约束不是障碍，是设计输入。**
6. **改别人的东西之前先确认「是不是我弄坏的」。** 我一度以为 `selectFeedbackType` 是自己删的 ——
   比对 diff 的 hunk 边界 + 自己那次 `old_string` 的范围才排除。**没确认就道歉/认账，也是一种不准确。**
7. **物理上做不到的事，要当场说清楚。** 「没打开也要弹」做不到，第一时间讲明白，
   免得做完才发现期望对不上。
