### 现象

### 排查过程（走过弯路，如实记）

**第一版假设**：以为 `tauri.dev.conf.json` 被读了但内容不对。
**验证方法**：往配置里塞一个独特字符串 `DEVCONF-MARKER-12345`，
编译后 `strings jizhi.exe | grep` 看它在不在。

**结果**：搜不到 → 我据此下了「dev 配置没被读」的结论。

**⚠️ 这个结论不能要 —— 检测方法本身是错的。** 补了对照组才发现：
base 配置里独有的 `12121e`（背景色）、`currentUser`、`SimpChinese` **同样搜不到**。
**配置文件根本不以明文串存进二进制**，搜不到证明不了任何事。

**第二版（有效）**：改标题、强制重建（`touch src/main.rs`，因为配置是编译期嵌进去的），
再读窗口标题——**仍是 `JIZHI`（base 的值），不是我设的 marker**。

**最终定论**：查 Tauri v2 的 CLI 二进制，里面硬编码的配置文件名**只有五个**：

```
tauri.android.conf.json   tauri.ios.conf.json   tauri.linux.conf.json
tauri.macos.conf.json     tauri.windows.conf.json
```

**没有 `.dev.` 这一档。** 官方文档也只列这五个。

### 结论

**`tauri.dev.conf.json` 从来没被读过。** 主窗口一直按 base `tauri.conf.json` 加载
`https://www.jizhi-learn.com` —— 那是 **09-18 的部署版**，我用离线方式查过它的 bundle：
`__TAURI__` / `set_pet_visible` / `桌宠` / `user_shortcuts` **全是 0 处**，
**零桌面端代码**。

这一条把四个现象一次解释通了：落地页、无窗口按钮、无 Vite 连接、我的诊断条不出现。

### ⚠️ 顺带更正 09-28 的一条结论

09-28 日志教训 #14 写的是「`tauri.dev.conf.json` 的 windows 数组把主配置整个盖掉，
导致 dev 没有桌宠窗口」。**这是误诊。** 真实情况是那个文件压根没被读 ——
dev 里桌宠不显示只是因为 base 配置写着 `visible: false`，

### 修法

会把生产安装包指到 `localhost:5173`，装出来的客户端直接白屏。

用 CLI 的 `--config`：

```json
"dev": "tauri dev --config src-tauri/tauri.dev.conf.json"
```

**验收信号**（改完必须看这三个，缺一不可）：
① Vite 上出现 **ESTABLISHED 连接**；② 落地页消失；③ 右上角出现窗口控制按钮。

## 三、桌宠：悬停轮盘

### 先测一条「不成立就全盘推翻」的假设

用户定的交互是「鼠标移进小基 → 轮盘显示 → **滑轮滑动选择** → 左键确认」。
而 **Windows 的滚轮默认发给有焦点的窗口** —— 用户工作时焦点在 PyCharm 上，
鼠标悬在桌宠上滚，事件可能压根到不了。

**实测**（把桌宠挪到空地、保持 PyCharm 有焦点、`SetCursorPos` + `mouse_event` 滚轮）：

| 步骤 | 鼠标位置 | 滚了 | 总次数 | 窗口内/外 |
|---|---|---|---|---|
| 基线 | —— | —— | 32 | 32 / 0 |
| A | 小基中心 | 5 格 | **37（+5）** | 37 / 0 |
| B | 远处 | 5 格 | **37（+0）** | 37 / 0 |

**结论：无焦点照样收得到，且只在鼠标悬停时收。** 设计成立，
**不需要在移入时 `setFocus()`** —— 那会在用户打字时把焦点夺走。

> ⚠️ 这次测试**第一遍是脏数据**：诊断只记总数不记坐标，读数 44 → 73 → 106，
> 而我只滚了 5 格。加上 `clientX/clientY` 判别（落在 0..220 内才算「悬停收到的」）
> 之后结论才干净。**观测手段分不清来源，数据就不能用。**

### 实现

`ui/pet.html` 重写。第一层四项：`🎙 语音` · `🎨 换个样子` · `⏱ 专注计时` · `👋 先躲起来`。

**两种特殊的层**（用户要的「每一层都这样做」）：

- `kind: 'look'` —— **滚动即预览**：滚到哪一项小基当场变脸，确认才固定，退回则还原
- `kind: 'dial'` —— **转盘**：滚动连续调时长（5–90 分钟 + 「停止」档），
  当前值固定在正上方，滚动时整圈数字一起变

**删掉的东西**：右键菜单、550ms 长按。它们和拖动抢同一个计时器，是「手抖就误触」的根源，
也正是用户说的「两步」。

### 三个自己踩的坑

| # | 现象 | 根因 |
|---|---|---|
| 1 | 鼠标移开轮盘不收 | 判断用的是**最后记录的鼠标坐标** —— 而 `mousemove` 只在窗口内触发，`mouseleave` 来时它**必然在窗口内**，判断永远说"还在里面"。改用 `mouseleave` 事件**自带**的坐标 |
| 2 | 「松开往左下角挪一点」 | 展开用 `center` 锚点、收起用**默认的右下角**，120px 的差变成位移。一开一收必须同一个锚点 |
| 3 | 小基贴屏幕右缘时轮盘被切掉 | 窗口从中心长大，右边那半圈跑出屏幕。Rust 侧按显示器范围夹取 |

另外把 `mousemove` 里的 `closeWheel()` 删了 —— 它要在拖动**同一瞬间**发一次异步改窗口尺寸的
IPC，和紧接着的 `startDragging()` 抢时序，拖起来会顿。

## 四、桌宠的设置页

`set_pet_size` 加 `anchor` 参数（`center` / 默认右下角）+ 屏幕范围夹取。

配置桥新增第三通道 `set_pet_prefs`。**桌宠与主窗口是两个 origin**，
同源策略下桌宠读不到主窗口的 localStorage，所以 token / 后端地址 / 偏好三样都得由主窗口推给壳。

### ⚠️ 设置不联动 —— 是轮询写错了

第一版桌宠轮询取配置，而且写成了：

```js
setInterval(async () => {
  if (!cfg.token) await loadCfg()     // ← 语义变成「只有还没拿到才去要」
}, 5000)
```

**token 一到就再也不回读**，于是设置页改了开关桌宠毫无反应。

改成**事件驱动**：`set_pet_prefs` 存下后 `emit("pet-prefs")`，桌宠监听后立刻重渲染。
**轮询只留作兜底**（而且去掉了那个守卫）。

### 设置页内容

- 显示桌宠开关
- **操作对照表**（唯一说明书：移入/滚轮/左键/右键/拖动/移开）
- **轮盘项开关**（4 项，至少留一项）
- **小基大小**：滑杆 0.6–1.6 连续可调，一个 `--s` CSS 变量贯穿形象/光环/圆点/名字条
- **开机自启**（`tauri-plugin-autostart`，状态**问壳要** —— 注册表 Run 项才是真相）

### ⚠️ 我埋过一个坑：给「先躲起来」做了开关

用户报「先躲起来怎么没了」。查下来代码里**它还在** —— 是用户在设置页把那个开关关掉了。

**那是我设计错了**：「先躲起来」是收起桌宠的**唯一入口**（没有托盘图标、没有别的恢复路径），
给它做开关 = 让用户能把自己锁在「桌宠常驻、关不掉」的状态里。

已改成 `pinned: true`：**不提供开关，永远在**，并且存坏的旧值也会被 `normalizePetPrefs` 纠正回来。

## 五、数据库：SQL 收尾

用户：「现在需要数据库的都给我，我一起执行了」。

### 做法

把 `backend/sql/` 下 **23 个脚本合并成一份**可重复执行的合集。逐个核对幂等性后发现：

- **19 个本来就能重复跑**
- **3 个不能**（`agent_center_tables` / `subject_plan_tables` / `vocab_tables`）——
  `CREATE POLICY` 没有 DROP 保护。**在合集里给每个前面补上匹配的 `DROP POLICY IF EXISTS`**
- 顺序按依赖排：建表 → 授权 → 补列/迁移 → 视频库修补 → RLS → 新增

### 第一次执行报错

```
ERROR: 42883: operator does not exist: uuid = text
```

定位到 `exam_paper_records.sql`：

```sql
user_id  TEXT NOT NULL,                                   -- ← 文本
CREATE POLICY "user_read_own" ... USING (auth.uid() = user_id);   -- ← auth.uid() 返回 uuid
```

**`uuid = '字面量'` 能跑（字面量会推断类型），只有跟另一列比才炸** —— 所以写的时候不容易发现。

修法是 `auth.uid()::text = user_id`，**不是**反过来写 `user_id::uuid`：
后者也能过编译，但**表里只要有一行不是合法 uuid 就直接抛错**，更危险。

扫了全部策略，**只有这一处**，其它清一色 `USING (true)`。

### 第二次执行：干净通过

自检确认所有表都在。

### ✅ 顺带结掉一个 09-27 的悬案

09-27 查 #7「社区收藏失败」/ #8「胶囊封存不了」时，我怀疑是
**`post_collects` / `countdowns` 表缺失** —— 但当时连不上 Supabase 的 `rest/v1`
（校园网 SNI 阻断），只能标「**未能证实**」，还特意在清单里放对照表防误判。

**现在证实了：表在。** 这两条病的**不是缺表**。

而生产上正常工作的接口走的是 service_role。下一步是查这两张表的 GRANT/RLS 状况。

## 教训

1. **观测手段分不清来源，数据就不能用。** 滚轮测试读数 44→73→106 而我只滚了 5 格 ——
   当时诊断只记总数不记坐标。加上 `clientX/clientY` 判别后才干净。
   **先问「这个数能不能区分我要区分的两种情况」，再去读它。**
2. **校验器本身要先验证 —— 本轮踩了两次。**
   ① 二进制字符串搜索：base 配置里独有的 `12121e` / `currentUser` **同样搜不到**，
   说明配置根本不以明文存进二进制，那个方法无效；
   ② 目录锚点检测器：`\s+` 合并空格 vs GitHub 逐空格转换，报了 10 条**假**断链。
   **两个方法我都差点拿它们下了结论。**
3. **两个 bug 可以互相掩盖，顺序修才看得见。** dev 配置坏 → `isDesktop` 恒为 false →
   顶层那段代码永远不执行 → Pinia 顺序错和缺 import 都藏得好好的。
   **修好 A 才炸出 B —— 不要以为"改一处就完事了"。**
4. **「死文件」比「错配置」更难查。** `tauri.dev.conf.json` 不是"配错了"，
   是**文件名根本不被识别**。没有任何报错，行为静默地和你预期不一样。
   **配置文件没生效时，先确认这个文件名认不认，而不是去读它的内容。**
5. **给一个功能做开关之前，先问「关掉它还能不能用」。**
   「先躲起来」是收起桌宠的唯一入口，我给它做了开关 —— 用户一关，桌宠就再也收不起来。
   **唯一出口不能是可选项。**
6. **同一件事的"开"和"关"必须用同一个锚点。** 展开 `center`、收起默认右下角，
   120px 的差在用户眼里就是「松开鼠标它自己挪了一点点」。
7. **`mousemove` 只在窗口内触发 —— 所以它记的坐标永远在窗口内。**
   拿它判断 `mouseleave` 等于用「必然为真」的条件做判断。**判断要基于事件自带的、可能为假的信号。**
8. **用户报「功能没了」时，先查是不是被自己加的开关关掉的。**
   我第一反应是"代码里明明有"，查下去才发现是我设计错了。
9. **一个报错可能只是第一个报错。** SQL 那次事务在 `exam_paper_records` 中途中止，
   **后面 18 个脚本一条都没跑过** —— 我没有假设"剩下的应该没事"，
   而是主动扫了下一个可能失败点（`ALTER TABLE` 引用不存在的表）。
   **排查一个错误之后，要问"还有没有同类的"，而不是"应该就这一个吧"。**
10. **动手前先确认方向 —— 这轮我又犯了一次。**
    用户说「继续搞桌面版」，我直接开始修 bug、起应用、加诊断，做到一半被叫停
    「你怎么改了桌面版」。**该先对齐"这一轮要达成什么"，再动文件。**

## 本机环境备注

- **`_probe_20260929/gen_sql.py`** 是 SQL 合集的生成器 —— 以后改完 `backend/sql/` 下的源文件，
  重跑它就能重新生成 `待执行SQL_20260929.sql`，不用手工拼。
- **PowerShell 脚本里别写中文**：GBK 控制台读 UTF-8 源码会解析失败
  （本轮 `wheeltest.ps1` 因此报了一串语法错）。
- 挪窗口位置时 `SetWindowPos` 的 `hWndInsertAfter` **不能传 `HWND_TOP`（0）** ——
  那会把 `alwaysOnTop` 的窗口**降级**成普通窗口，之后被别的窗口盖住。
  要保置顶就传 `HWND_TOPMOST`（-1）。
