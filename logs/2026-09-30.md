## 三、🎯 根因：缺 GRANT（三层掩盖）

用户质疑「有一些不是已经有的数据表拉取数据吗，不能都是 0 吧」——
**他是对的，我话说过了头**。实测只有 4 张缺 GRANT 的表读不到，
仪表盘的「用户总数 22 / 总答题数 8 / 总学习计划数 2」从来就不是 0。

### 实测结果（service_role 探测线上）

```
用户总数      profiles             OK   22
总答题数      question_records     OK    8
待处理举报    content_reports      403   ← 缺 GRANT
待处理反馈    user_feedback        403   ← 缺 GRANT
```

**为什么能断定是缺 GRANT 而不是 RLS**：Supabase 的 `service_role` 自带 `BYPASSRLS`；
RLS 拦截的表现是「200 + 空数组」，而 **42501 是表级 `insufficient_privilege`**。

**根因一目了然**：`admin_tables.sql` 建了 5 张表，**整个文件一条 GRANT 都没有**。
而项目里其它 7 个 SQL 文件都有 —— `grant_exam_paper_records.sql` 甚至就是为修同一个坑建的。

### 三层掩盖

```
① 缺 GRANT  → 42501
② 后端      → if res.status_code != 200: return []      ← 伪装成"没有数据"
③ 仪表盘    → except Exception: pass → 恒为 0            ← 伪装成"业务上就是 0"
```

### 更严重：用户反馈根本没存进去过

```python
# feedback.py:29-43
try:
    await client.post(f"{SUPABASE_URL}/rest/v1/user_feedback",
                      headers=get_admin_headers(),   # ← service_role，被 42501 拒
                      json={...})
except Exception as e:
    logger.info(f"反馈存DB失败（不影响邮件发送）: {e}")   # ← 没有状态码检查
```

**httpx 不对 4xx 抛异常** → `except` 根本不触发 → 用户看到「感谢反馈」，库里一行没有。

## 五、处置闭环：禁言 / 封禁真的生效

### 设计取舍

- **状态不查新表**。每次请求都要判，所以判在 `profiles` 上 ——
  认证中间件**本来就已经在查 profiles**（判管理员角色），加两个列零额外开销。
- `user_sanctions` 只存**历史**（谁、因为什么、多久、谁操作、是否解除），不参与热路径。
- 加 **30 秒进程内缓存**：封禁不是秒级敏感操作，为此让每个 API 多一次往返不划算。

### 生效点

- **封禁** → 接在 `get_current_user` 的**两个**认证出口上
  （自签 JWT 是本地验证的，不查库根本发现不了，只挂一处会漏）
- **禁言** → 接在发帖 / 评论入口，按 `mute_scope` + 到期时间拦，**到期自动失效，不需要定时任务**

### 举报处置一步到位

`PUT /admin/reports/{id}/resolve` 支持六种动作：
`dismiss` / `mark` / `warn` / `delete_content` / `mute`(1·7·30天·永久) / `ban`
—— 判定、处罚、回写举报记录、审计留痕一次完成，带回读校验。

### 端到端实测（用库里现成的「测试用户」账号，用完还原）

```
① 基线：发评论 → 400（越过禁言检查，在后面因假 post_id 失败）→ 未误拦
② 禁言 7 天 → profiles.muted_until = 2026-10-07T04:03:28Z，处置历史写入
③ 发评论 → 403「你已被禁言，暂时无法评论（解禁时间 2026-10-07 12:03）」 ✅
④ 封禁 → profiles.is_active = false
⑤ 发评论 → 403「账号已被封禁，如有疑问请联系管理员」                     ✅
⑥ 还原 → is_active=true, muted_until=null
```

第 ③ 步的 **12:03** 是北京时间（库里的 04:03 UTC + 8），时区换算也对。

## 六、全面 API 检测：145 个端点

用户：「都检验一下调用API，输出是否有问题，全面检测并修复」。

### ⚠️ 其中一个是我自己引入的回归

我把 7 处「非 200 降级成空」改成抛 502 时，**漏了 PostgREST 的 `206 Partial Content`**：

> 只要总数超过一页（带 `Prefer: count=exact` + `limit` 的查询几乎总是如此），
> 响应就是 **206** 而不是 200 —— 只认 200 的检查会把**正常响应**当成故障。

| 端点 | 症状 |
|---|---|
| `GET /admin/users` | **502**（22 个用户、每页 20 → 第一页恒为 206） |
| `GET /admin/dashboard` | **7 个指标全变 0** |

已修 16 处检查。修后：用户列表 200、仪表盘 `total_users: 22` + `errors: {}`。

> 讽刺的是：这个检查**在修之前也是错的** —— 那时它把 206 降级成空列表，
> 所以用户列表其实一直是空的，只是没人看得出来。**我把它从「静默错」变成了「响亮错」，
> 然后才找到真因。**

### ⚠️ 我误建的脏数据（已清）

探测 `POST /admin/questions` 时发空 body，**它当场建了一道 content 全 null 的题**。
已删除，题库总数回到 **19338**。修法：加必填校验 + `exclude_unset=True` + 写后回读。

### 修掉的问题

| 端点 | 修前 | 修后 |
|---|---|---|
| `DELETE /admin/announcements/{不存在}` | 200「已删除」 | 404 |
| `PUT /admin/feedback/{不存在}` | 200「已处理」 | 404 |
| `PUT /admin/qa/{不存在}` | 200「已处理」 | 404 |
| `POST /admin/questions`（空 body） | **建脏题** | 400 题干不能为空 |
| `GET /admin/settings` | `syllabus_count: 0` | 17 |

根因是 PostgREST 的 PATCH/DELETE **不区分「改了 1 行」和「匹配 0 行」，都是 204**。

### 社区模块：anon key 权限不足（09-27 悬案结案）

### 8.3 为窗口按钮让出一条（`--jz-top`）

用户：「全部页面的内容都要往下一点点，因为右上角的6个按钮会遮挡内容」。

窗口按钮是 `position:fixed` 悬浮的（`top:10px right:20px`，高 32px），压在内容上。

```css
:root            { --jz-top: 0px; }
html.jz-desktop  { --jz-top: calc(48px / var(--jz-scale, 1)); }   /* 桌面壳才加这个类 */
html.jz-desktop .app-container { padding-top: var(--jz-top); }
```

同时把**全站 55 处**「满屏高度」改成 `calc(100vh - var(--jz-top, 0px))` ——
否则加了 padding 会让满屏页多出 48px、把滚动条又推回窗口（就是刚修掉的那个）。
**网页版 `--jz-top` 为 0px，渲染结果与改动前完全一致。**

⚠️ **必须除以 `--jz-scale` 做反向补偿**：按钮写的是 `calc(32px / var(--jz-scale))`
为的是缩放后物理尺寸恒定；留白写死的话，窗口一缩小留白跟着缩、按钮不变，又会压回内容。

## 教训

1. **探测权限要把四种动词都测一遍。** 我第一轮只测 SELECT，
   于是漏掉 `profiles` 缺 UPDATE —— 而这一条卡死了禁言/封禁/改角色三件事。
   **「能读」和「能写」是两回事。**
2. **`!= 200` 这个判断在本项目里是错的。** PostgREST 返回部分数据时用 **206**。
   任何带 `count=exact` + `limit` 的查询，只要总数超过一页就恒为 206。
3. **「静默降级成空」会把所有故障伪装成同一个样子。** 42501、表不存在、网络错、
   越权，全长得像「暂无数据」。**修一个 bug 之前，先确保你能看见它。**
4. **同一个 bug 可能被修过两次，但只修了症状。** 09-27 把 `/community/collections`
   的「静默返回空列表」改成了显式报错 —— 但根因（anon 无权限）没动，
   所以它从「显示暂无收藏」变成了 502，**功能一直是坏的**。
5. **改动前后都要问「这个判断在别的状态码下成立吗」。** 我修 A 引入了 B。
6. **往跑着 HMR 的页面里插诊断代码，一次只改一处。** 模板和 script 分两次编辑，
   中间那个半成品状态会被当成真错误。今天栽了两次（App.vue 的 `onMounted`、
   AdminLayout 的 `authStore`）。
7. **grep 会连注释一起命中。** 我用 `min-height:100vh` 扫出「32 处要改」，
   其中一部分是我自己写在注释里的解释文字。**报数之前先看一眼命中的是什么。**
8. **探针自己会产生副作用。** 用空 body 探 `POST /admin/questions`，
   它真的建了一道脏题。**探测写端点要用幽灵 id 或先确认它会拒绝。**
9. **修一半比不修更危险。** `author_id` → `user_id` 改了列名，但没发现
   service_role 对 `posts` 没权限 —— 改了也是 403。**要修就修到底。**
10. **用户说「不能都是 0 吧」的时候，他是对的。** 我拿「故障时的表现」当成了现状描述，
    把范围说大了。**下结论前先量一遍。**

## 教训（接上一节，11 起）

11. **报「不一致」之前，先确认测量本身是完整的。** 我用 `curl -s` 拉线上主 JS 做 md5 比对，
    报出「线上与本地不同」—— 实际是**下载被截断**（904,140 / 1,173,006 字节），
    而 `-s` 把 curl 自己的报错也一起静音了。补上 `Content-Length` 对照、
    重下带错误检查之后：**逐字节一致**。**差点据此下「前端没部署」的结论。**
12. **对照实验只有在「有区分度」时才成立。** 我想用「exe 里有没有 localhost 字符串」
    区分 dev 构建与生产构建，结果**两个 exe 都有** —— 那串来自 Tauri capability 的
    远程源白名单（生产源 + 开发源一起授权），**不是窗口配置**。
    先问「这个信号在两种情况下会不会不一样」，再去读它。
13. **写在文档里的步骤，不等于会被读到。** `pip install` 这条我写进了 `DEPLOY.md`、
    在对话里也提醒过，用户**还是先重启了服务**。**打包那一刻就该把步骤顶到最前面。**
14. **「现象」和「原因」之间隔着一层渲染逻辑。** 「落地页没更新」听起来像部署没生效，
    实际是 `v-if` 把一个条件渲染的按钮藏了。**别从现象直接跳到部署链路。**
15. **同名文件是最容易传错的一类。** 两个安装包同名、同版本号、内容不同。
    **没有校验和，肉眼分不出** —— 以后凡是「同名但内容不同」的产物，
    一律先记 md5。
